Development journey: how the course made its own turbulence dataset

The course planned to train on the Johns Hopkins Turbulence Database (JHTDB). It ended with a dataset from its own 256³ simulation. Between those two points are one numerical blow-up, two discarded production runs, and two wrong conclusions by the agent. This page records all of them.

Evidence. This page is a reconstruction. An agent wrote it after the work, from six session transcripts on disk, the git history, the private handoff file and the published files in data/dns/. The agent recomputed the final-run values in Section 5 from those files. The failed runs were deleted, so their numbers come only from transcripts and cannot be measured again. Tool output in the extract used for this page was cut at 1500 characters per block; the agent read the raw transcript where it needed more.

1. The brief

The course joins continuum kinematics, flow matching and turbulence statistics. Its laboratory must train a generative model on three-dimensional turbulent velocity fields, then judge the samples by physical statistics. So the course needs a dataset of such fields. At the start, none of the five source repositories held one.

The owner chose the kind of data in one line: "1 3d dataset". The same message answered three other questions: "2 you can check my local computer configuration", "3 yes PyTorch", "4 links". The owner did not name a data source. The agent recommended JHTDB.

2. Starting context

The agent measured the machine before it recommended anything. The machine has an NVIDIA GeForce RTX 3050 Laptop GPU with 4096 MiB. PyTorch 2.11.0 with CUDA 12.8 worked. A short benchmark of a small 3D flow-matching model (1.42 M parameters) on 64³ fields used 1281 MiB and 143 ms per step at batch 2, and 2536 MiB and 380 ms per step at batch 4. The primary record of that benchmark is a transcript only.

Three conditions shaped the work and are not visible in the code:

  • All agent replies were in ASD-STE100 Simplified Technical English, under a standing rule of the owner.
  • A "ponytail" hook pushed the agent toward the smallest working code.
  • A cost monitor printed warnings when a session grew large. It warned at about 272k context tokens in the first session and at about 447k in the fifth. The owner cleared the context between sessions, so HANDOFF.md carried the state of the work.

DNS means direct numerical simulation: a solver that computes all scales of the flow from the Navier–Stokes equations, with no turbulence model. The memory, time and Reλ values in the table were estimates or published typical values, and the agent said so at the time. The owner asked for the full explanation to go into the course, so it is in Section 4 of the lab page.

The agent also corrected the premise of the owner's question: one computer cannot generate "JHTDB data". JHTDB is one specific simulation from a supercomputer. A new run can have the same physics but not the same numbers.

3.2 The training fields

The model trains on 64³ fields, because the GPU cannot train on 256³. The simulation produces them in two ways, and the two ways are the sampling choice that chapter 3 teaches. A filtered field applies a sharp cutoff, |ki| < 32, then uses the 64³ grid: it covers the whole periodic box and has no aliasing. A crop is a contiguous 64³ block of the 256³ field: it keeps the full resolution, but it is not periodic.

3.3 The solver

The solver copies the method in the JHTDB README where it can, so the two datasets have the same physics. It uses a periodic box [0, 2π)³, the rotational form of the equations, an integrating factor for the viscous term, and the JHTDB forcing rule: after each step, the modes with 0 < |k| ≤ 2 are rescaled so that their total energy stays constant. It differs in two ways. It uses third-order Runge–Kutta in place of Adams–Bashforth, and the 2/3 de-aliasing rule in place of a phase shift. The arrays are float32, because of the GPU memory.

The forcing rule amplified both later faults. The faults were in code that did not remove roundoff, so the rule stayed unchanged and the forcing still matches JHTDB.

4.1 The pivot from JHTDB

The JHTDB client installed in a clean environment (givernylocal 3.6.4). A 16³ cube came back in 1.6 s. The 64³ test failed with a clear message:

Exception: too many points requested for the testing authorization token: 262144 > 4096

an authorization token can be requested by email from turbulence@lists.johnshopkins.edu
 include your name, email address, institutional affiliation and department, together with a short description of your intended use of the database

The agent called the token the only blocker. It listed 1000 blocks of 64³ at about 3.1 GB, and it recorded that a contiguous block spans only 1/16 of the domain per side. The owner deferred the token. Six author agents then drafted the chapters, and chapters 3 and 6 assumed JHTDB data. That text was later rewritten.

The token request asks for personal and institutional details. The agent drafted an email, and it named a 64³ DNS as a fallback. The owner then chose to skip the token "to expedite the project". The transcripts have no record that a request went out, so it is not known whether JHTDB would have refused.

The reason for the pivot was the token step. No measured defect in JHTDB caused it, and JHTDB remains the higher-Reynolds-number dataset: Reλ 418 against 115. labs/jhtdb_fetch.py stays as an optional script. It ran for two 16³ cubes only.

4.2 The first hour of the solver

The self-test of labs/dns_isotropic.py found two faults within one minute. In the first, the dissipation was summed over rounded shells. The agent changed the sum to use the exact |k| of each mode, and the residual fell from 4.1e-02 to 4.9e-05:

energy budget residual / eps 4.1e-02, divergence 2.9e-07, k fell 0.5000 -> 0.3007
AssertionError: energy budget (nonlinear term must conserve k)

The second was an index error in the 64³ filter, with an error of 2.9e-01 against a limit of 1e-5. After the correction the error was 2.7e-07:

filtered64 against subsampling of a band-limited field 2.9e-01
AssertionError: filtered64 index mapping

All checks then passed at 32³, but the first 256³ steps looked wrong: ε = 5.77 in the starting field, where the corrected code gives about 0.014, and kmaxη = 0.52. Shell 128 held energy 0.0878, and 68 modes above k² = 400 sat in the plane kz = 128. The starting field makes a round trip through real space, and cuFFT had put its non-conjugate part into that highest-frequency plane. The agent applied the de-aliasing mask again after the round trip. That fix covered the starting field only. The same FFT behavior inside the time loop later cost one run, and the agent did not test for it at this point.

Then the 256³ spin-up failed:

blow-up at t = 0.400; lower --dt

The time-stepping method was Heun, a second-order Runge–Kutta method. It slowly amplifies pure advection, and at 256³ the viscosity did not damp the smallest waves fast enough. The agent replaced it with third-order SSP Runge–Kutta, and the spin-up passed t = 0.4. The change raised the cost per step: Heun took 174 to 190 ms and the new method about 260 ms, with different GPU load in the two measurements. Memory was 2113 MiB allocated and 2460 MiB reserved, against an estimate of about 1.3 GB.

4.3 Run 1: a skewness that the agent dismissed

The first run looked good. At t = 9 it gave ε = 0.108 against 0.103 for JHTDB, and kmaxη was 1.40 against 1.35. Its step time rose from 261 ms to as much as 469 ms during spin-up. The probable cause is another program on the same GPU, which used 3602 MiB at 100 % load in an earlier test. The agent did not stop it. The step time was 263 ms when production started.

During the run, the owner asked for the status. The agent reported a gradient skewness of −0.97 at t = 86.8, against −0.4 to −0.6 before t = 20. It added: "One logged value fluctuates, so this value alone is not an error." That conclusion was wrong, and the next status report said so. Gradient skewness measures the asymmetry of velocity differences, and real turbulence gives about −0.4 to −0.5. The change lasted for more than 10 time units:

The kinetic energy, the dissipation, Reλ and kmaxη stayed in their normal ranges, so the routine log lines hid the fault.

The run also stopped. Its last log line is at t = 90.4, with no done line. It was a child process of the session, and the harness listed 4 background tasks that "didn't finish before the previous session ended". This cause is probable, not proved. The agent found the stop three hours later, when the owner asked for the status again.

The owner wrote "resume the run". The agent restarted it as a separate process, so that a later session end could not stop it. The first logged step gave the same k and skewness as the earlier run, k = 0.5762 and −1.212 at t = 90.4. So the restart was exact, and the fault was already in the saved state. The restart also left duplicate rows for t = 90.2 and 90.4 in stats.csv, and the earlier restart command in the handoff would have overwritten the log, because it used > and not >>.

4.4 First diagnosis: a mean flow from roundoff

After the run ended at t = 111, the agent measured the skewness in three directions. All three had moved, to about −1.3, so one large eddy in one direction was not the cause. The agent then looked at the mean flow, which should be zero. It was not:

t527277111
Mean-flow energy2.2e-68.8e-56.5e-30.19 (k is 0.67)

The agent explained this as follows. A real-valued field has a Fourier transform in which the coefficient at −k is the complex conjugate of the coefficient at k. The code stores half of the spectrum, but its kz = 0 plane holds both k and −k separately. Rounding errors break the conjugate rule in that plane. That broken part belongs to no real field, so the cascade cannot drain it. The forcing amplifies it, the GPU FFT maps it into the highest-frequency plane, and from there it aliases into the mean flow. The mean flow has no viscous damping, because viscous damping is proportional to k².

A 64³ test reproduced it between t = 10 and t = 120. Without a fix, the mean-flow energy rose from 1.0e-13 to 3.7e-3. With a new function Grid.clean(), it stayed exactly 0.

The fix removed a real fault, but it was not the cause of the skewness rise. The agent marked the gap at the time: "Not yet proven: that the fix also restores the skewness at 256³. The new run must show this." Its later status reports still treated the mean flow as the cause.

The agent did not use the first 72 time units of run 1, although they looked usable. Its reason: "the published script must be the script that made the data". This rule cost 2.1 hours and kept the record consistent.

4.5 Run 2: the same symptom without a mean flow

Run 2 wrote to data/dns_fixed/. During the run, the owner repeated the agent's question and answered it: "After the new run passes its check, can I delete the 3.6 GB in data/dns/ and put the new data in its place? yes." This approval depended on a pass.

Near the end of the run, the agent reported on snapshots up to t = 83: mean-flow energy at most 3.9e-18, skewness −0.38 to −0.59, and "the fault that corrupted the old run has not come back". That statement was true only up to t = 83. Eight minutes later it no longer held. At t = 96 the full-grid skewness was −1.04. The agent reported that it now doubted its explanation.

The run finished with all 100 snapshots, and it failed:

The flow had stopped being homogeneous turbulence. Enstrophy, the squared vorticity, had collected in a small part of the box. The agent deleted nothing, because the approval required a pass. It gave the owner three options:

  1. Find the cause first, with about 20 minutes of small tests. The agent recommended this.
  2. Use only the snapshots of the clean-looking window, t = 12 to 81.
  3. Change the forcing and rerun, at 2.1 hours or more. The new forcing would not match JHTDB, and the rerun might not fix anything.

Option 2 was a near-miss. The agent's reason for option 1 was that slow roundoff growth could already be present inside that window. It was. The window would have carried a divergent energy of 2.7e-4 at t = 72 and 1.5e-3 at t = 78, and those fields would have been published as clean data.

The agent also recorded a possible physical cause: real long-time behavior of constant-energy forcing. If the course had accepted that without a test, the published text would have described a solver bug as physics.

4.6 Second diagnosis: the divergent part of the velocity

The test had one simple idea. Rounding errors are about 5.4e8 times smaller in float64 than in float32. So if roundoff is the seed, a float64 run must fail later. If the forcing causes the failure physically, the precision must not matter. The agent ran 64³ tests with ν = 0.01 and Δt = 0.016 at about 61 ms per step.

The first batch lost its per-mode forcing runs to a bug in the test script:

RuntimeError: imag is not implemented for tensors with non-complex dtypes.

After a fix to the script, a second batch ran. Time of the failure, defined as flatness above 5.5 for 10 time units:

64³ run, old codeStart of the failure
float32, 3 seedst = 112, 114, 122
float64, seed 0t = 262 (t = 263 with half the time step)
float64, seed 2t = 247
float64, seed 1no failure by t = 300

This separated the cases. The failure depends on precision, so the seed is roundoff. It does not depend on the time step, so it is not a time-stepping error. A test of one dominant mode and a test of helicity did not explain the start of the failure.

The agent then looked for a part of the state that could grow from roundoff with no mean flow. An incompressible velocity must have zero divergence: k · û = 0 for each mode. The function rhs() projected only the nonlinear term. Nothing ever projected the velocity itself. So any rounding error in k · û stayed in the state. A measurement on the 64³ filtered fields of run 2 showed this energy:

t12425466727890102111
Divergent energy4.3e-122.1e-87.4e-73.0e-52.7e-41.5e-33.3e-20.130.17

At t = 111 this energy is 0.17 of a total k of 0.52, about 32 %. In every printed row the largest mode is (−1, −1, 1), which is inside the forced band. The energy outside the band adds almost nothing: at t = 12 the two totals are 4.28e-12 and 4.56e-12, and from t = 24 onward they agree to the printed digits. The transcripts do not establish why that one mode wins and not another mode.

The mechanism gives a rate that a measurement can test. The forcing keeps the band energy Ef constant, against the loss ε to the cascade, so it multiplies each band amplitude at the rate ε/(2Ef). A normal mode loses the same energy to the cascade. A divergent component has no nonlinear transfer, because the projection removed it from the term that would transfer it. It has only viscous decay. Its net amplitude rate is therefore:

rate = eps / (2 E_f) - nu k^2
     = 0.096 / (2 x 0.3075) - 0.002 x 3
     = 0.150          (predicted)
       0.146          (measured on run 2, t = 16 to 76)

The agent did not fit that rate to the data. It computed the prediction from independent values, and the two values differ by about 3 %. This number is the reason to accept this diagnosis and not the earlier one.

For this page, the agent also checked the size of the float32-to-float64 delay. It did not compute this during the session, so it is a later consistency check, not part of the diagnosis. The ratio of machine precisions, 5.4e8, is 20.1 e-folds. The measured delays run from 125 to 150 time units (247 − 122 to 262 − 112), which implies an amplitude rate of 0.13 to 0.16. That is the same order as 0.150. The 64³ tests use ν = 0.01, so their true rate is not the 256³ rate, and the agent did not measure it.

The fix is one line: clean() now returns self.project(uh). The agent tested it in float32, with 3 seeds at 64³, to t = 500, which is 4.1 to 4.5 times the old failure time of t = 112 to 122. Divergent energy stayed at or below 1.9e-16, flatness stayed at 4.06–4.23 (100-unit means), and skewness stayed at −0.43 to −0.47.

The check became a tool. labs/check_dns.py prints FAIL on data/dns_fixed, with the first sustained rise at snapshots 73 to 75. So the check failed on the real fault before it was used for acceptance.

No inertial range. The first draft of chapter 3 used a synthetic field with a prescribed spectrum, so its fitted slope of −1.634 came back close to −5/3 by construction. The real data gave a different result. The compensated spectrum has its maximum, 2.494, at shell 9, and no other shell is within 5 % of it. A count-corrected version peaks at 2.283 with only shells 7 to 9 inside the tolerance. So the data have no band in which to test the −5/3 law. A hand-picked fit over shells 4 to 12 gives −1.699, only 0.032 from −5/3. Moving the ends gives −1.362, −1.873, −1.933 and −2.438. Chapter 3 now shows this spread as a warning against hand-picked fits. The size table in Section 4.2 of the lab page expected about half a decade of inertial range at 256³. That estimate used typical published values and no 5 % rule. The measurement found no band.

Time correlation. The integral time is 2.297, and the correlation at a lag of 7 is 0.047. The 100 snapshots hold 21.91 independent samples. The 74 training fields hold 16.34 and the 20 test fields hold 4.79. Chapter 6 uses these measured values in place of two unverified JHTDB time scales, 1.99 and 0.572, that its first draft had used. All values from run 2 (T of about 2.2, about 16 samples) are void.

Lab 2 on the data. One run of labs/lab2_generative_turbulence_3d.py --data filtered --batch 2 --iters 30000 --guard 6 took 3.24 hours (11 672 s). It does not support the study claim of chapter 6:

  • The energy ratio of generated to reference is 0.661 at shell 1. The other 30 shells stay within a factor of 1.25, so the criterion fails only at shell 1. The total energy is 0.857 of the reference (0.5235 against 0.6107).
  • Flatness passes, at 2.73 against 2.82.
  • Gradient skewness misses its limit of 0.1 in 1 of 3 directions, with a difference of 0.117.
  • The memorization test was not computed, because Lab 2 does not have it.

A detector that failed its control. The spectral-collapse detector of chapter 5, Section 5.11 assumes Gaussian scatter in its tolerance. On this data, two reference fields, which it should accept, depart in 9 of 10 pairs. Generated fields depart in 24 of 32 pairs. So the detector cannot separate the two groups on this flow. The measured scatter at shell 20 is 8 times the assumed value. The lab page states this. Chapter 5 is unchanged, because any edit voids its review acceptance. The held-out control found this result.

Reviews of the revised chapters. The reviewers found faults in the claims about the data, not in the proofs. Chapter 3 said the spectrum "stays within 5 %" for shells 9 to 25, but only 9 of those 17 shells did. Chapter 6 stated its nearest-neighbor bound in the wrong direction: a lower bound of 0.953 where the measured median is 0.823. A later round found that the text gave a Gaussian field a flatness miss of about 0.08. A simulation of 800 fields gave a per-field flatness of 2.94, and that value replaced the claim. No script in the repository produces 2.94.

7. What went wrong, and the fixes

  1. JHTDB token limit. too many points requested for the testing authorization token: 262144 > 4096. Not fixed. The course stopped using JHTDB as its data source.
  2. Energy budget in the first self-test. AssertionError: energy budget (nonlinear term must conserve k). Residual 4.1e-02. After the fix, 4.9e-05.
  3. Filter index error. AssertionError: filtered64 index mapping. Error 2.9e-01. After the fix, 2.7e-07.
  4. False energy in the starting field. No error message. ε = 5.77 and kmaxη = 0.52 at 256³ with all self-tests passing, because the self-tests ran at 32³. The agent masked the field again after the round trip through real space.
  5. Syntax fault from a patch. E901 TokenError: unterminated f-string literal, at line 285 and again at line 291. A patch script left a broken f-string in the solver, and its first repair failed in the same way. A third patch corrected the escaping.
  6. Heun blow-up. blow-up at t = 0.400; lower --dt. The agent replaced the method. It did not lower the time step.
  7. Dismissed skewness. The agent called −0.97 one fluctuating value. The fault was real. Rule learned: look at the window mean before you explain one value.
  8. Session end stopped the run. The run stopped at t = 90.4 with no error. The agent had warned that a clear "can stop it", but it still ran the job as a background task of the session. Later runs were detached processes.
  9. Unsafe restart command. The handoff used > where it needed >>, and the restart repeated the rows for t = 90.2 and 90.4 in stats.csv. The agent corrected the command, and the analysis had to remove the duplicates.
  10. Mean-flow fault. Mean-flow energy of 0.19 at t = 111. clean() now enforces the conjugate rule on the kz = 0 plane and sets the mean flow to zero.
  11. Premature conclusion. "the fault that corrupted the old run has not come back", from data up to t = 83, when the old fault had shown only from about t = 72 to 111. Rule learned: a test that ends before the failure region is not a pass.
  12. Divergence fault. Divergent energy of 0.17 at t = 111, and flatness of about 28. clean() now projects the velocity.
  13. Test harness bug. RuntimeError: imag is not implemented for tensors with non-complex dtypes. The per-mode forcing runs passed a real tensor to energy(). The agent fixed the script and ran a second batch.
  14. A wrong docstring. The docstring of clean() first gave the mean flow as the cause of the skewness rise. The agent corrected it after the second diagnosis.
  15. GPU contention. Another program on the GPU probably raised the DNS step time from 261 to as much as 469 ms in spin-up. Lab 2 took 753 ms per step in its middle 6000 steps, against about 298 ms elsewhere, while review agents ran. The cause of the Lab 2 change was not isolated. The DNS and Lab 2 cannot share the 4096 MiB card, so they ran in sequence.
  16. Budget estimate. The Lab 2 estimate of 1.19 GPU-hours came from a short probe of 143 ms per step. The measured 298 ms gives about 2.5 hours, 2.1 times as long.

  • A reader cannot reproduce runs 1 and 2 exactly, because the old code was never committed and the old data is deleted. The folder became a git repository only at publication. Removing parts of clean() reproduces the behavior class, not the same numbers.
  • Another machine or library gives a different realization of run 3 with the same statistics, not the same digits, because turbulence is chaotic.
  • The result is one run at one Reynolds number. The Lab 2 outputs are single stochastic runs.
  • The GPU benchmark table, the 1790 and 2106 MiB memory test at 256³ with the fix, the 1.6 s cutout, the JHTDB token limits and the 72 GB size of The Well have only transcript records. They were not rechecked before publication.

9. Where things stand

The dataset is final and its statistics are public in data/dns/. The snapshots are not in the repository; WORKFLOW.md in the repository gives the commands that regenerate them. The first command took 2.13 hours on the machine above.

Unfinished, by decision. Each item below has a cost, and the course stands without it:

  • JHTDB at 64³. Never run, because there is no token. It needs a token request. It would add a Reynolds number of 418 and an inertial range. labs/jhtdb_fetch.py is ready, but its commands were not run at that size.
  • Memorization test of Lab 2. Claim (iii) of chapter 6 stays untested. Adding it needs a rerun of about 2.5 hours.
  • Detector tolerance. Replacing the Gaussian tolerance of chapter 5, Section 5.11 with one from the measured scatter needs a new review of chapter 5.

Knowledge captured. The clean() docstring in labs/dns_isotropic.py holds the two fault mechanisms and their numbers. WORKFLOW.md holds the commands and the evidence limits. Section 4 of the lab page holds the size trade-offs. The private HANDOFF.md holds the resume state. No general memory entry records these faults.

Rules this work supports.

  • A forcing that rescales a band amplifies anything in that band that the cascade cannot drain. Audit what the nonlinear term cannot touch.
  • Make a run print each quantity that must stay zero. Mean-flow energy and divergent energy were not in the log of run 1.
  • Test a roundoff hypothesis by changing the precision. Test a mechanism by predicting its rate before you measure it.
  • A check must fail on a known-bad case before it can accept a good one.
  • Do not delete failed data until the replacement passes. The second diagnosis needed the fields of run 2.
